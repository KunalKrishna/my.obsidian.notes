🗺️ The Software Separation in RAM
**Off-Heap** memory refers to any physical RAM allocation that sits **outside the strict boundaries of the garbage-collected JVM Heap sandbox**. To understand this concept clearly, look at how the JVM splits your physical computer memory:
```
[ YOUR COMPUTER'S PHYSICAL RAM STICKS ]
 ├── [ ON-HEAP MEMORY (The Sandbox) ]  ─────> Managed entirely by the JVM Garbage Collector.
 │                                           Bound by the `-Xmx` flag.
 │
 └── [ OFF-HEAP MEMORY (The Open Range) ] ──> Managed directly by the JVM Native C++ Engine 
                                             or the host OS Kernel.
                                             (Includes Metaspace, Code Cache, and Stacks).
```

⚙️ Why Does Java Use Off-Heap Memory?
If Java is famous for its automated heap management, why does it push so many critical architectural components (like Metaspace, Code Cache, and Thread Stacks) out to the off-heap native memory area?

There are three primary reasons:
1. Protection from Garbage Collection Pauses: If **Class Metadata Blueprints** (Metaspace) or **Compiled Hardware Binaries** (Code Cache) were stored on the main heap, the GC would constantly have to scan through millions of complex, unchangeable structural system pointers.
2. Direct Hardware Execution: The **Code Cache** must live off-heap because it contains raw binary instructions that need to be fed directly into the physical CPU core circuits without any intermediate translation or software buffering software layers
3. High-Performance I/O (Networking & Disks) : When you use Java NIO (New Input/Output) to read a file or stream data across a network network socket, the JVM utilizes an off-heap buffer called **Direct Byte Buffers**.

>[!question]- Where do these abstract logical concepts represented in JVM Architecture actually live?
>- **Physically:** Every single byte of your running Java application—regardless of the component name—lives in the exact same physical **RAM sticks**.
>- **Logically & Administratively:**
>    - **The Heap Area** is a closed sandbox **strictly managed by the JVM's Garbage Collector** and constrained by `-Xmx`.
>    - **The Rest (Metaspace, Stacks, Code Cache)** are **managed by the JVM's native C++ engine** using raw, off-heap memory requested dynamically from the **OS Kernel**.
>

## Heap Structure

**One line:** The shared runtime area where all objects live, split into generations so the GC can collect efficiently.

The heap is created at JVM startup, **shared across all threads**, and holds every object and array you `new`. It's divided into generations based on object age:

```
┌──────────────────────── HEAP ───────────────────┐
│                                                 │
│   ┌─────────── Young Generation ────────────┐   │
│   │  ┌────────┐  ┌──────────┐  ┌──────────┐ │   │
│   │  │  Eden  │  │ Survivor │  │ Survivor │ │   │
│   │  │        │  │   S0     │  │   S1     │ │   │
│   │  └────────┘  └──────────┘  └──────────┘ │   │
│   └─────────────────────────────────────────┘   │
│                                                 │
│   ┌─────────── Old Generation (Tenured) ────┐   │
│   │            long-lived objects           │   │
│   └─────────────────────────────────────────┘   │
│                                                 │
└─────────────────────────────────────────────────┘
```

```
[─────────────────────────────────── TOTAL JVM HEAP AREA ─────────────────────────────────────────]
│                                                                                                 │
│  [───────────── YOUNG GENERATION ─────────────]    [────────────── OLD GENERATION ───────────]  │
│  ┌─────────────────┬─────────────────┬────────┐    ┌─────────────────────────────────────────┐  │
│  │                 │   Survivor S0   │ Suv S1 │    │                                         │  │
│  │   Eden Space    │  (From Space)   │ (To)   │    │            Tenured Space                │  │
│  │  (Birthplace)   ├─────────────────┴────────┤    │          (The Retirement Home)          │  │
│  │                 │    Empty or Swapping     │    │                                         │  │
│  └─────────────────┴──────────────────────────┘    ├─────────────────────────────────────────┤  │
│                                                    │  🟢 String Pool (String Table)          │  │
│                                                    │  🔵 java.lang.Class Objects             │  │
│                                                    │      (Houses Static Fields & Primitives)│  │
│                                                    └─────────────────────────────────────────┘  │
[─────────────────────────────────────────────────────────────────────────────────────────────────]
```

>[!note]- Conceptual view of Heap Area : Older GC pov vs Modern GC pov
>The neat, continuous "Young vs. Old" box layout described above is exactly how older collectors (like Parallel GC) physically slice your RAM. However, if your application uses modern collectors like **G1 GC** or **ZGC**, the Heap layout changes from "big boxes" to a **grid matrix**.
>
>```
>[──────────────── Modern G1/ZGC Region Heap Layout ────────────]
>│  [ Eden ]  [  Old ]  [ Surv ]  [  Old ]  [ Free ]  [ Eden ]  │
>│  [ Old  ]  [ Free ]  [ Eden ]  [ Surv ]  [  Old ]  [ Free ]  │
>│  [ Free ]  [  Old ]  [ Free ]  [ Free ]  [ Eden ]  [  Old ]  │
>[──────────────────────────────────────────────────────────────]
>```
>
>- Under G1 or ZGC, the heap is broken up into thousands of tiny, equal-sized **Regions**.
>- Each individual region is dynamically assigned a label: some are Eden regions, some are >Survivor regions, and some are Old regions.
>- **The point:** Even though the physical memory layout becomes a mixed grid, the >**logical concept remains identical**. Objects are still born in an Eden region, age in a >Survivor region, and get promoted to an Old region along with the String Pool and static >Class objects!


- **Eden** — where brand-new objects are allocated. Most objects are born and die here.
- **Survivor spaces (S0, S1)** — objects that survive a Young GC get moved here. Only one is in use at a time; GC copies survivors between them.
- **Old Generation (Tenured)** — objects that survive enough GC cycles get "promoted" here. These are your long-lived objects (caches, singletons, session data).
![[jvm - heap area 1.png]]

![[Pasted image 20260725134645.png]]
**The lifecycle of a typical object:** allocated in Eden → survives a Minor GC → copied to a Survivor space → survives several more → promoted to Old Gen (or dies along the way and is collected). _(The GC mechanics dealt in [[Module 5 — Garbage Collection]]— this note is just the layout.)_

```java
public class HeapDemo {
    public static void main(String[] args) {
        // Every 'new' below allocates on the heap, in Eden first
        String s = new String("hello");   // object -> heap
        int[] nums = new int[1000];        // array  -> heap
        Object o = new Object();           // object -> heap
        // s, nums, o are references on the STACK pointing INTO the heap
    }
}
```

_Interview Q: "Walk me through the heap layout."_ → Young (Eden + 2 Survivors) and Old gen; objects start in Eden and get promoted to Old if they live long enough.

## Stack & Stack Frames

**One line:** A **per-thread area** holding method-call frames; each frame has that method's local variables and workspace. Purely automatic — no GC involved.

Every thread gets its **own** stack (unlike the shared heap). Each time a method is _called_, a new **stack frame** is pushed; when the method _returns_, its frame is popped. LIFO, like a stack of plates.

Each frame contains:
- **Local Variable Array** — the method's parameters and local variables (primitives stored directly; object variables stored as _references_ into the heap).
- **Operand Stack** — a scratch workspace the bytecode uses to compute expressions.
- **Frame Data** — reference to the constant pool, return address, etc.

```java
public class StackDemo {
    public static void main(String[] args) {   // frame 1 pushed
        int x = 10;                             // x lives in frame 1's locals
        int result = square(x);                 // calling square...
        System.out.println(result);
    }                                           // frame 1 popped

    static int square(int n) {                  // frame 2 pushed
        int sq = n * n;                         // n, sq live in frame 2's locals
        return sq;
    }                                           // frame 2 popped, control back to main
}
```

At the moment `square` runs, the stack looks like:

```
│  square frame  │  <- top (locals: n=10, sq=100)
│  main frame    │      (locals: x=10, args, result)
└────────────────┘
```

**`StackOverflowError`** happens when frames pile up faster than they pop — classic cause is unbounded recursion:

```java
static void recurse() {
    recurse();   // no base case -> frames never pop -> StackOverflowError
}
```

_Interview Q: "What's on the stack vs the heap?"_ → Stack holds per-thread frames with locals and references; heap holds the actual objects those references point to. And: infinite recursion → `StackOverflowError`.

## Metaspace (vs PermGen)

**One line:** Both store _class metadata_ (PermGen also stored objects & static variables). PermGen was a fixed slice of the heap; Java 8 replaced it with Metaspace, which lives in **native memory** and grows automatically.

Metaspace separates structural data (blueprints) from runtime state data (objects).
- **Metaspace** strictly and exclusively stores the **structural blueprints/Class Metadata** (method bytecode tables, annotation registries, and constant pools). No business data or execution states live here.
- **The Main Heap** holds all **runtime state data and objects**. Every time you use the `new` keyword, or modify an object's instance variable, that dynamic data is written to the Heap.

Visual Nested Box Model

```
[ COMPUTER'S PHYSICAL RAM STICKS ]
 ├── [ JVM HEAP BOUNDARY ] ─────────> Stores: Objects, String Pool, java.lang.Class Mirrors
 └── [ NATIVE OS MEMORY (OFF-HEAP) ]
       ├── [ METASPACE ] ────────────> Stores: Class Metadata (Uncompiled Bytecode)
       ├── [ CODE CACHE ] ───────────> Stores: JIT-Compiled Native Machine Code Binary 💥
       └── [ THREAD STACKS ] ────────> Stores: Local variables and execution frames
```

```

[ PHYSICAL HARDWARE: RAM ]
   └── [ SOFTWARE ZONE: METASPACE ] (The physical off-heap storage space) : managed by OS Kernel (not JVM)
         └── [ OVERARCHING DATA FOLDER: CLASS METADATA ] (The complete blueprint for a Class)
               ├── 1. Method Bytecode Tables (The execution logic)
               ├── 2. Annotation Registries (The structural tags)
               ├── 3. Runtime Constant Pool (The string/index lookup)
               └── 4. InstanceKlass Headers (The identity and rules)
```

This is one of the most-asked "do you know your Java versions" questions.

>[!question]- 🧱 What Exactly is Contained in Class Metadata?
>When you compile a `.java` file into a `.class` file, the Java compiler packages several pieces of metadata that the JVM reads during the **Loading** phase:
>- **The Class Hierarchy:** The name of the class, its package, its superclass (parent), and any interfaces it implements.
>- **The Field Table:** A complete inventory of all variables declared in the class, including their names, data types, and modifiers (`public`, `private`, `static`).
>- **The Method Bytecode Table:** A list of all methods, their return types, parameter requirements, and the actual raw **bytecode instructions** that execute when the method is called. 
>- **The Runtime  Constant Pool:** A massive internal lookup index table containing strings, numerical constants, method references, and class names referenced by the bytecode. 
>- **Annotation Data:** Any structural annotations (like `@Override`, `@Component`, or `@Entity`) attached to classes, fields, or methods.

| Data Category                                                                   | Java 7 & Older (PermGen Era) | Java 8+ (Metaspace Era) | Why it was changed / Interview Catch                                                                            |
| ------------------------------------------------------------------------------- | ---------------------------- | ----------------------- | --------------------------------------------------------------------------------------------------------------- |
| **Class Metadata**  <br>_(Blueprints, method tables, fields)_                   | 📥 **PermGen**               | 📥 **Metaspace**        | This is the _only_ data category that stayed in the same conceptual zone (moved to native memory).              |
| **Method Bytecode**  <br>_(Actual execution instructions)_                      | 📥 **PermGen**               | 📥 **Metaspace**        | Stored directly within the structural class metadata blueprint.                                                 |
| **Runtime Constant Pool**  <br>_(Symbolic reference placeholders)_              | 📥 **PermGen**               | 📥 **Metaspace**        | The structural lookup tables stay attached to the class metadata.                                               |
| **Static Primitive Fields**  <br>_(e.g., `static int count = 5`)_               | 📥 **PermGen**               | 🛑 **Main JVM Heap**    | Moved to the Heap. They are attached to the `java.lang.Class` instance.                                         |
| **Static Object References**  <br>_(e.g., `static User admin = ...`)_           | 📥 **PermGen**               | 🛑 **Main JVM Heap**    | Both the reference pointer and the target object now live completely on the Heap.                               |
| **String Literals / Interned Strings**  <br>_(e.g., `"hello"`, `str.intern()`)_ | 📥 **PermGen**               | 🛑 **Main JVM Heap**    | Moved out of PermGen back in Java 7 to allow the standard Garbage Collector to reclaim text memory efficiently. |


>[!note]- Method Area vs Metaspace
>**The Method Area** is an _abstract concept_ defined in the Java specification, while **PermGen** and **Metaspace** are _physical implementations_ of that concept.

**PermGen (Java 7 and earlier):**
- Lived _inside_ the heap, with a **fixed maximum size** (`-XX:MaxPermSize`).
- Because it was fixed, loading too many classes (common in big app servers, or with lots of dynamic class generation) caused the dreaded `java.lang.OutOfMemoryError: PermGen space`.
![[Pasted image 20260725134724.png]]
**Metaspace (Java 8+):**
- Moved _out_ of the heap into **native memory** (OS memory = RAM, not JVM heap).
- **Grows automatically** by default — no fixed cap unless you set one with `-XX:MaxMetaspaceSize`.
- This mostly eliminated the classic PermGen OOM, though a leak (e.g., classloaders never released) can still exhaust it: `OutOfMemoryError: Metaspace`.

```
Java 7:   [ ---- HEAP ---- | PermGen ]             PermGen inside heap, fixed size
Java 8+:  [ ---- HEAP ---- ]   +   [ Metaspace ]   Metaspace in native memory, auto-grows

				[Method Area] (abstract concept defined in Java Specs)
					 | 
					 | Physical implementation
					 ▼
	┌──────────────────────────────┐
	│                              │   
    ▼                              ▼
till Java 7                    since Java 8
[PermGen ]                      [Metaspace]
- part of JVM Heap memory     - in Native OS Memory (RAM)
- `-XX:MaxPermSize=256m`      - no max fixed size (`-XX:MaxMetaspaceSize`)
- class Metadata   ---------> - class Metadata
- Runtime Constant Pool-----> - RCP (Symbolic reference placeholders)
- interned String  --------->  (Moved to the Main Heap)              
- static variables --------->  (Moved to the Main Heap)
```

>[!note]- **Both the Heap Area and Native OS Memory live in the exact same physical RAM** inside your computer.
>The CPU makes no physical distinction between them. The difference between them is entirely a **software architecture distinction** created by the Operating System (OS) and the JVM.
>```
>[ PHYSICAL HARDWARE ]  ──────────────────────> [  YOUR COMPUTER'S PHYSICAL RAM  ]
>                                                        │              │
>[ SOFTWARE BOUNDARIES (OS & JVM) ]                     ▼              ▼
>                                              [ JVM HEAP BOUNDARY ]  [ NATIVE OS MEMORY ]
>                                              (Managed by JVM GC)   (Managed by OS Kernel)
>```
>Replacing PermGen (Heap) with Metaspace (Native Memory) provided several critical technical advantages beyond simply avoiding the dreaded `java.lang.OutOfMemoryError`
>* **The JVM Heap** is a single, contiguous block of virtual memory that the JVM explicitly requests from the Operating System at startup (configured by `-Xms` and `-Xmx`). The JVM acts as its own internal operating system within this block, managing allocations and running Garbage Collection cycles manually.
>* **Native OS Memory** is the remaining "open range" of RAM managed directly by the host Operating System kernel. Any application (like a web browser, a C++ program, or the JVM itself) can ask the OS for chunks of this memory dynamically at runtime.

| Feature                      | Java 7 (PermGen)                   | Java 8+ (Metaspace)                   |
| ---------------------------- | ---------------------------------- | ------------------------------------- |
| **Physical Location**        | Inside JVM Heap                    | Inside Native OS Memory (Off-Heap)    |
| **Allocated By**             | JVM's internal memory manager      | host Operating System Kernel          |
| **Sizing Model**             | Fixed maximum size (Manual bounds) | Dynamically grows by default          |
| **Stores Class Metadata?**   | Yes                                | Yes                                   |
| **Stores Static Variables?** | Yes                                | **No** (Moved to the Main Heap)       |
| **Stores Interned Strings?** | Yes                                | **No** (Moved to the Main Heap)       |
| **Primary Crash Type**       | `OOM: PermGen space`               | `OOM: Metaspace` (Only if restricted) |
| **Max Boundary Flag**        | `-XX:MaxPermSize=256m`             | `-XX:MaxMetaspaceSize=256m`           |

## PC Register & Native Method Stack

**One line:** Two small per-thread areas — the PC Register tracks which instruction is executing, and the Native Method Stack supports calls into non-Java (native) code.

Short note — know they exist and their role.

**Program Counter Register** — each thread has one. It holds the address of the JVM instruction _currently_ being executed. Because each thread has its own PC, the JVM can pause a thread, switch to another, and later resume exactly where it left off. (For native methods, the PC value is undefined.)

**Native Method Stack** — a separate stack used when Java calls **native methods** (methods written in C/C++ via JNI, the Java Native Interface). When code calls something like a native OS-level function, execution uses this stack instead of the normal Java stack.

```java
public class NativeDemo {
    // 'native' = implemented in C/C++, not Java. Uses the Native Method Stack.
    public native void doNativeWork();

    // Real example: System.currentTimeMillis() is a native method under the hood
    public static void main(String[] args) {
        long t = System.currentTimeMillis(); // dips into native code
        System.out.println(t);
    }
}
```

_Interview Q: "What's the PC Register / Native Method Stack?"_ → PC Register: per-thread pointer to the current instruction (enables thread switching). Native Method Stack: supports native (JNI/C/C++) method calls.

## Heap vs Stack (Comparison)

**One line:** **Stack** = per-thread, holds frames/locals/references, auto-managed, fast, small. **Heap** = shared, holds objects, GC-managed, larger, slower. The single most common memory comparison question.

| Aspect              | Stack                                              | Heap                                  |
| ------------------- | -------------------------------------------------- | ------------------------------------- |
| **Shared?**         | Per-thread (private)                               | Shared across all threads             |
| **Stores**          | Frames: local variables, references, operand stack | Objects and arrays (the actual data)  |
| **Managed by**      | Automatic (push on call, pop on return)            | Garbage Collector                     |
| **Size**            | Small (set via `-Xss`)                             | Large (set via `-Xmx`/`-Xms`)         |
| **Speed**           | Very fast (just moves a pointer)                   | Slower (allocation + GC overhead)     |
| **Error when full** | `StackOverflowError`                               | `OutOfMemoryError: Java heap space`   |
| **Lifetime**        | Tied to method call                                | Until no references remain, then GC'd |

The example that ties it together — one line of code touches both:

```java
Person p = new Person("Alice");
```

- `new Person("Alice")` → the **object** is created on the **heap**.
- `p` → the **reference** (a pointer to that heap object) is stored on the **stack**, in the current frame's local variables.

```
   STACK (current frame)          HEAP
   ┌───────────────┐             ┌──────────────────┐
   │ p  ───────────┼────────────▶│ Person object    │
   │               │             │  name = "Alice"  │
   └───────────────┘             └──────────────────┘
```

So when people ask "is `p` on the stack or the heap?" the precise answer is: **the reference `p` is on the stack; the object it points to is on the heap.**

_Interview Q: "Difference between stack and heap?"_ → use the table; anchor it with the `Person p = new Person()` example (reference on stack, object on heap).
