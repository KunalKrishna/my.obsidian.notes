# PART 1 — THE PROBLEM: WHY NORMALIZATION EXISTS

---
## 1.1 The "God Table" Anti-Pattern

When databases are naively designed, all data is often crammed into one large table. Observe:

**Table: EMP\_PROJECT (Deliberately Terrible — Starting Point)**

| EmpID | EmpName | EmpPhone | DeptID | DeptName | DeptLoc | ProjID | ProjName | ProjBudget | HrsWorked |
|---|---|---|---|---|---|---|---|---|---|
| E1 | Alice | **9876, 8765** | D1 | Engineering | Block A | P1 | Alpha | 500000 | 20 |
| E1 | Alice | **9876, 8765** | D1 | Engineering | Block A | P2 | Beta | 300000 | 15 |
| E2 | Bob | 7654 | D1 | Engineering | Block A | P1 | Alpha | 500000 | 10 |
| E3 | Carol | 6543 | D2 | Marketing | Block B | P3 | Gamma | 200000 | 30 |
| E4 | Dave | **5432, 4321** | D2 | Marketing | Block B | P2 | Beta | 300000 | 25 |
| E4 | Dave | **5432, 4321** | D2 | Marketing | Block B | P3 | Gamma | 200000 | 12 |

Even before running a single query, problems are VISIBLE:
- Alice's name and department appear **twice** (rows 1, 2)
- "Engineering" department info appears **three times** (rows 1, 2, 3)
- "Alpha" project info appears **twice** (rows 1, 3)
- EmpPhone has **multiple values in one cell** (rows 1, 2, 5, 6)

---
## 1.2 The Four Core Problems (Anomalies)

### Anomaly 1: Data Redundancy

The same fact is stored in multiple places.

```sql
"Engineering is in Block A" — stored in rows 1, 2, and 3.
"Alpha's budget is 500000" — stored in rows 1 and 3.
```

**Consequence:** Wastes storage, creates multiple points of failure for consistency.
### Anomaly 2: Update Anomaly

A single real-world change requires updating MULTIPLE rows. Missing even one creates inconsistency.

```sql
Scenario: Engineering department relocates from Block A → Block C

UPDATE EMP_PROJECT SET DeptLoc = 'Block C' WHERE DeptID = 'D1';

→ Must update ROWS 1, 2, AND 3.
→ If Row 2 is missed → rows 1 and 3 say Block C, row 2 still says Block A.
→ Database is now INCONSISTENT for the same department!
```
### Anomaly 3: Insertion Anomaly

Cannot record a fact about one entity without having data about a related (but independent) entity.

```sql
Scenario: New project P4 "Delta" (budget: 400000) is approved.
No employee assigned yet.

INSERT INTO EMP_PROJECT VALUES (NULL, NULL, NULL, NULL, NULL, NULL, 'P4', 'Delta', 400000, NULL);

→ EmpID is part of the Primary Key → cannot be NULL!
→ The project data is HELD HOSTAGE by employee data.
→ Cannot record the project's existence until an employee is assigned.
```
### Anomaly 4: Deletion Anomaly

Deleting one entity's data accidentally destroys data about a completely different entity.

```sql
Scenario: Carol (E3) leaves the company.

DELETE FROM EMP_PROJECT WHERE EmpID = 'E3';

→ Row 4 is deleted.
→ ALL information about project Gamma (P3 — name, budget) is GONE!
→ The project likely still exists, but we've lost its record
   because it was tied to Carol's assignment.
```
### Anomaly 5: Multi-valued Attribute Problem

```sql
EmpPhone: "9876, 8765" — two phone numbers in ONE cell

→ Cannot query: SELECT * WHERE Phone = '8765'   (won't match "9876, 8765")
→ No standard format enforced
→ Cannot count distinct phone numbers
→ Violates the foundational principle: one cell = one value
```

These five problems are the entire **motivation for normalization**.

# PART 2 — PREREQUISITE CONCEPTS
---
## 2.1 Functional Dependency (FD)

### Definition
> In a relation R, attribute set X **functionally determines** attribute set Y (written **X → Y**) if and only if: for any two tuples t1 and t2 in R, whenever `t1[X] = t2[X]`, it must follow that `t1[Y] = t2[Y]`.

**Plain English:** Knowing the value of X lets you uniquely identify the value of Y.
### Examples from EMP\_PROJECT

```sql
EmpID  → EmpName              ✅ Knowing employee ID determines their name
EmpID  → DeptID               ✅ Each employee belongs to one department
DeptID → DeptName, DeptLoc    ✅ Each dept has one name and location
ProjID → ProjName, ProjBudget ✅ Each project has one name and budget

(EmpID, ProjID) → HrsWorked   ✅ Hours worked requires BOTH employee and project

EmpName → EmpID               ❌ Multiple employees can share a name
DeptName → EmpID              ❌ Many employees can be in one department
```
## 2.2 Types of Functional Dependencies

### 2.2.1 Full Functional Dependency
Y is **fully** functionally dependent on X if:
- X → Y, AND
- Removing ANY single attribute from X breaks the dependency

```sql
Example: (EmpID, ProjID) → HrsWorked is FULL because:
  EmpID alone  ↛ HrsWorked  (same employee works different hours on diff projects)
  ProjID alone ↛ HrsWorked  (same project has different employees with diff hours)
  ONLY the combination (EmpID, ProjID) → HrsWorked  ✓ FULL FD
```
### 2.2.2 Partial Functional Dependency
Y is **partially** dependent on composite key X if Y is also determined by a PROPER SUBSET of X.

```sql
Example: (EmpID, ProjID) → EmpName is PARTIAL because:
  EmpID alone → EmpName  (EmpName doesn't change based on ProjID)
  So EmpName is "partially" dependent — it only needs PART of the composite key.

  ⚠️ Partial dependencies ONLY exist when there's a COMPOSITE key.
     If PK is a single column, partial dependencies are impossible.
```
### 2.2.3 Transitive Functional Dependency
Y is **transitively** dependent on X if there exists Z such that:
X → Z, and Z → Y, where Z is NOT a superkey and Z is not a subset of any candidate key.

```c
Example: 
  EmpID → DeptID   (direct)
  DeptID → DeptName (direct)
  ∴ EmpID → DeptName (TRANSITIVE — through the intermediate DeptID)

  Chain: EmpID ──→ DeptID ──→ DeptName
                   ↑
          (DeptID is the intermediate non-key attribute)
```
### 2.2.4 Trivial vs Non-trivial FD

| Type                       | Definition                           | Example                  |
| -------------------------- | ------------------------------------ | ------------------------ |
| **Trivial**                | X → Y where Y ⊆ X (Y is subset of X) | {EmpID, EmpName} → EmpID |
| **Non-trivial**            | X → Y where Y ⊄ X                    | EmpID → EmpName          |
| **Completely non-trivial** | X → Y where X ∩ Y = ∅                | EmpID → DeptName         |
Only **non-trivial** FDs matter for normalization analysis.
## 2.3 Key Terminology for Normalization

| Term | Definition | Example |
|---|---|---|
| **Superkey** | Any set of attributes that uniquely identifies rows | {EmpID}, {EmpID, EmpName}, {EmpID, ProjID} all work |
| **Candidate Key (CK)** | Minimal superkey — no redundant attributes | {EmpID} is CK (EmpName not needed) |
| **Primary Key (PK)** | Chosen candidate key | EmpID |
| **Prime Attribute** | Belongs to ANY candidate key | If CK = {EmpID, ProjID}, both are prime |
| **Non-prime Attribute** | Belongs to NO candidate key | EmpName, DeptName, etc. |

> ⚠️ **Critical distinction:** The prime vs non-prime distinction is the backbone of 2NF and 3NF definitions. Know it well.

## 2.4 Armstrong's Axioms (Rules for FD Reasoning)

| Axiom | Rule | Meaning |
|---|---|---|
| **Reflexivity** | Y ⊆ X ⟹ X → Y | A set determines any of its subsets |
| **Augmentation** | X → Y ⟹ XZ → YZ | Can add same attrs to both sides |
| **Transitivity** | X → Y, Y → Z ⟹ X → Z | Chain FDs together |
| **Union** (derived) | X → Y, X → Z ⟹ X → YZ | Combine right-hand sides |
| **Decomposition** (derived) | X → YZ ⟹ X → Y and X → Z | Split right-hand sides |
## 2.5 Properties of a Good Decomposition

When a table is broken into smaller tables during normalization:

```c
Property 1: LOSSLESS JOIN (Non-additive Join)
  When you re-JOIN all decomposed tables, you get EXACTLY the original table.
  No spurious (phantom) tuples appear. No original data is lost.
  ✅ ALL normal forms guarantee this (otherwise the decomposition is wrong).

Property 2: DEPENDENCY PRESERVATION
  Every FD from the original table can be checked in ONE of the decomposed
  tables WITHOUT needing to join multiple tables together.
  ✅ 1NF, 2NF, 3NF always guarantee this.
  ⚠️ BCNF may NOT preserve all dependencies — this is the key 3NF vs BCNF tradeoff.
```

## 3.0 UNNORMALIZED FORM (UNF) — The Starting Point

### Definition
> A relation is **Unnormalized** if it contains **non-atomic values** — cells that hold multiple values, lists, sets, or repeating groups.
### Our UNF Table

| EmpID | EmpName | **EmpPhone** | DeptID | DeptName | DeptLoc | ProjID | ProjName | ProjBudget | HrsWorked |
|---|---|---|---|---|---|---|---|---|---|
| E1 | Alice | **9876, 8765** | D1 | Engineering | Block A | P1 | Alpha | 500000 | 20 |
| E1 | Alice | **9876, 8765** | D1 | Engineering | Block A | P2 | Beta | 300000 | 15 |
| E2 | Bob | 7654 | D1 | Engineering | Block A | P1 | Alpha | 500000 | 10 |
| E3 | Carol | 6543 | D2 | Marketing | Block B | P3 | Gamma | 200000 | 30 |
| E4 | Dave | **5432, 4321** | D2 | Marketing | Block B | P2 | Beta | 300000 | 25 |
| E4 | Dave | **5432, 4321** | D2 | Marketing | Block B | P3 | Gamma | 200000 | 12 |

**Violations:**
- `EmpPhone` holds a **list of phone numbers** in a single cell
- Cells are not indivisible/atomic

## 3.1 FIRST NORMAL FORM (1NF)

### Formal Definition
A relation R is in **1NF** if and only if:
1. Every attribute domain contains **only atomic (indivisible) values**
2. Every column contains only a **single value** from its domain
3. All values in a column are of the **same data type**
4. Every row is **uniquely identifiable** (a primary key exists)
5. There are **no repeating groups** of columns (no Phone1, Phone2, Phone3...)
6. Row order and column order are **irrelevant**
### Intuitive Explanation
> **"One cell, one value."** A phone column holds a phone number — not a list of numbers. An address column holds one address, not multiple addresses.
### Common 1NF Violations and Fixes

| Violation | Bad Example | Fix |
|---|---|---|
| Multi-valued cell | Phone: "9876, 8765" | Separate table with one phone per row |
| Composite attribute | Address: "123 Main, City, 12345" | Split into street, city, zip columns |
| Repeating column groups | Phone1, Phone2, Phone3 | Separate table |
| Non-atomic | Skills: "Java, Python, C++" | Separate table |
| Array in cell | Tags: [urgent, billing, VIP] | Separate table |

### Achieving 1NF: Fixing Our Table

**Strategy:** Move multi-valued `EmpPhone` to a separate table. The remaining table's PK becomes **(EmpID, ProjID)**.

### Functional Dependency Analysis After 1NF

In EMP\_PROJ\_1NF with PK **(EmpID, ProjID)**:

```
Prime attributes:     EmpID, ProjID
Non-prime attributes: EmpName, DeptID, DeptName, DeptLoc, ProjName, ProjBudget, HrsWorked

FD1: EmpID → EmpName                    ← PARTIAL  (only EmpID needed, not full PK)
FD2: EmpID → DeptID                     ← PARTIAL  (only EmpID needed)
FD3: DeptID → DeptName, DeptLoc         ← TRANSITIVE (EmpID→DeptID→DeptName/DeptLoc)
FD4: ProjID → ProjName, ProjBudget      ← PARTIAL  (only ProjID needed, not full PK)
FD5: (EmpID, ProjID) → HrsWorked        ← FULL FD ✅ (entire PK needed)
```

### ✅ What 1NF Solved

| Problem | Status |
|---|---|
| Multi-valued EmpPhone cell | ✅ Fixed — each phone is its own row |
| Non-atomic values | ✅ Fixed — every cell holds one value |
| Phone number queries possible | ✅ `WHERE Phone = '8765'` now works |

### ❌ What 1NF Did NOT Solve

| Problem | Still Present? | Root Cause |
|---|---|---|
| Alice's info stored twice (rows 1, 2) | ❌ Still there | EmpName partially depends on EmpID |
| Engineering info stored 3 times | ❌ Still there | DeptName partially/transitively depends |
| Alpha project info stored twice | ❌ Still there | ProjName partially depends on ProjID |
| Update anomaly (change dept location) | ❌ Still there | Multiple rows hold same dept data |
| Insertion anomaly (add project without employee) | ❌ Still there | ProjID is part of composite PK |
| Deletion anomaly (lose project on emp delete) | ❌ Still there | Project data tied to emp-project row |

**Root cause of remaining problems:** PARTIAL FUNCTIONAL DEPENDENCIES — non-prime attributes depend on only PART of the composite PK, not the whole thing.

**→ Solution: 2NF**

## 3.2 SECOND NORMAL FORM (2NF)

### Formal Definition
A relation R is in **2NF** if and only if:
1. It is in **1NF**, AND
2. Every **non-prime attribute** is **fully functionally dependent** on the **entire candidate key** — no partial dependencies exist

> **Partial Dependency** = A non-prime attribute that depends on a PROPER SUBSET of a candidate key.

> ⚠️ **Important:** 2NF is only relevant when there is a **composite candidate key**. A relation with a single-column PK that is in 1NF is automatically in 2NF.

### Identifying Partial Dependencies in EMP\_PROJ\_1NF

```sql
Composite PK: (EmpID, ProjID)

Checking each non-prime attribute:

EmpName  → Does it need both EmpID AND ProjID?
           NO! EmpID alone → EmpName. ∴ PARTIAL DEPENDENCY ❌

DeptID   → Does it need both EmpID AND ProjID?
           NO! EmpID alone → DeptID. ∴ PARTIAL DEPENDENCY ❌

DeptName → Does it need both EmpID AND ProjID?
           NO! EmpID → DeptID → DeptName. ∴ PARTIAL (transitive) ❌

DeptLoc  → Same as DeptName. ∴ PARTIAL (transitive) ❌

ProjName → Does it need both EmpID AND ProjID?
           NO! ProjID alone → ProjName. ∴ PARTIAL DEPENDENCY ❌

ProjBudget → Same as ProjName. ∴ PARTIAL DEPENDENCY ❌

HrsWorked → Does it need both EmpID AND ProjID?
            YES! EmpID alone ↛ HrsWorked (same emp works diff hours on diff projs)
            YES! ProjID alone ↛ HrsWorked (same proj has diff employees at diff hours)
            ∴ FULL FUNCTIONAL DEPENDENCY ✅
```

### Achieving 2NF: Decompose to Remove Partial Dependencies

**Rule:** For each partial dependency (PartialKey → Attributes), create a separate table with that partial key as PK, and move the dependent attributes there. Remove them from the original table.

**Decomposition Plan:**

```sql
Partial FD 1: EmpID → EmpName, DeptID, DeptName, DeptLoc
              → Create EMPLOYEE table with PK: EmpID

Partial FD 2: ProjID → ProjName, ProjBudget
              → Create PROJECT table with PK: ProjID

Full FD:      (EmpID, ProjID) → HrsWorked
              → Keep as WORKS_ON table (this IS the meaningful relationship)
```

### How 2NF Fixed the Anomalies

```sql
INSERTION ANOMALY — Project with no employee:
  BEFORE (1NF): INSERT INTO EMP_PROJ VALUES (NULL, ..., 'P4', 'Delta', 400000, NULL)
                → FAILS! NULL in part of composite PK not allowed.
  AFTER  (2NF): INSERT INTO PROJECT_2NF VALUES ('P4', 'Delta', 400000)
                → ✅ WORKS! Project exists independently in its own table.

DELETION ANOMALY — Deleting Carol:
  BEFORE (1NF): DELETE removes only row with E3, which happens to be Gamma's only row
                → ALL of Gamma's data (name, budget) is GONE.
  AFTER  (2NF): DELETE FROM EMPLOYEE_2NF WHERE EmpID = 'E3'
                → ✅ Gamma (P3) still exists safely in PROJECT_2NF.
                   WORKS_ON_2NF loses (E3, P3) row, but project data is preserved.

UPDATE ANOMALY — Change Alpha's budget:
  BEFORE (1NF): Must update 2 rows (wherever P1 appears).
  AFTER  (2NF): UPDATE PROJECT_2NF SET ProjBudget = 600000 WHERE ProjID = 'P1'
                → ✅ ONE row updated. Single source of truth.
```

### FD Analysis in EMPLOYEE\_2NF

```sql
EMPLOYEE_2NF(EmpID, EmpName, DeptID, DeptName, DeptLoc)
PK: EmpID
Prime attributes: EmpID
Non-prime: EmpName, DeptID, DeptName, DeptLoc

FDs:
EmpID → EmpName     ✅ EmpID is the PK, so this is fine
EmpID → DeptID      ✅ EmpID is the PK, direct dependency
DeptID → DeptName   ⚠️ DeptID is a NON-PRIME attribute determining DeptName (non-prime)
DeptID → DeptLoc    ⚠️ DeptID is a NON-PRIME attribute determining DeptLoc (non-prime)

Transitive chain:
EmpID ──→ DeptID ──→ DeptName
                └──→ DeptLoc
```

### ❌ What 2NF Did NOT Solve

| Problem | Still Present? | Root Cause |
|---|---|---|
| Engineering info stored TWICE (E1 and E2 both have D1 data) | ❌ Still there | Transitive: EmpID → DeptID → DeptName/DeptLoc |
| Update anomaly (Engineering moves to Block C — must change 2 rows) | ❌ Still there | DeptLoc depends on DeptID, not directly on EmpID |
| Insertion anomaly (can't add Department D3 without an employee) | ❌ Still there | Dept data lives inside Employee table |
| Deletion anomaly (delete Alice + Bob → lose Engineering dept info) | ❌ Still there | Dept data not stored independently |

**Root cause of remaining problems:** TRANSITIVE FUNCTIONAL DEPENDENCIES — a non-prime attribute (DeptID) is determining other non-prime attributes (DeptName, DeptLoc).

**→ Solution: 3NF**

## 3.3 THIRD NORMAL FORM (3NF)

### Formal Definition
A relation R is in **3NF** if and only if:
1. It is in **2NF**, AND
2. For every **non-trivial** functional dependency X → A in R, at least ONE of:
   - X is a **superkey** of R, OR
   - A is a **prime attribute** (member of some candidate key)

**Alternative informal definition:**
> No non-prime attribute is transitively dependent on any candidate key. Non-prime attributes must depend DIRECTLY on candidate keys only, not on other non-prime attributes.

**Simplest test:**
> If you find a non-key column determining another non-key column → 3NF is violated.

### Identifying Transitive Dependencies in EMPLOYEE\_2NF

```sql
EMPLOYEE_2NF: (EmpID, EmpName, DeptID, DeptName, DeptLoc)
PK (Candidate Key): {EmpID}
Prime attribute: EmpID
Non-prime attributes: EmpName, DeptID, DeptName, DeptLoc

Checking FD: DeptID → DeptName
  Is DeptID a superkey?    NO  ❌
  Is DeptName a prime attr? NO  ❌
  ∴ 3NF VIOLATED!

Checking FD: DeptID → DeptLoc
  Is DeptID a superkey?    NO  ❌
  Is DeptLoc a prime attr?  NO  ❌
  ∴ 3NF VIOLATED!

The transitive chain:
  EmpID → DeptID → DeptName
  EmpID → DeptID → DeptLoc

  DeptID is a "non-key intermediary" passing dependency transitively.
```

### Achieving 3NF: Decompose to Remove Transitive Dependencies

**Rule:** For each transitive dependency (NonKeyAttr → OtherAttrs), create a separate table with NonKeyAttr as PK, and move OtherAttrs there. Keep NonKeyAttr in the original table as a Foreign Key.

**Decomposition Plan:**

```sql
Transitive FD: DeptID → DeptName, DeptLoc
               → Create DEPARTMENT table with PK: DeptID
               → EMPLOYEE keeps DeptID as FK (the link is preserved)

Result:
  EMPLOYEE(EmpID, EmpName, DeptID[FK])
  DEPARTMENT(DeptID, DeptName, DeptLoc)
```

### How 3NF Fixed the Remaining Anomalies

```sql
INSERTION ANOMALY — Adding new department without employees:
  BEFORE (2NF): Dept data lives inside EMPLOYEE; must add an employee first.
  AFTER  (3NF): INSERT INTO DEPARTMENT_3NF VALUES ('D3', 'HR', 'Block C')
                → ✅ WORKS! DEPARTMENT exists independently.

DELETION ANOMALY — Both Alice and Bob leave:
  BEFORE (2NF): Deleting E1 and E2 removes the ONLY record of D1 Engineering.
  AFTER  (3NF): DELETE FROM EMPLOYEE_3NF WHERE EmpID IN ('E1','E2')
                → ✅ D1 Engineering still safely exists in DEPARTMENT_3NF.

UPDATE ANOMALY — Engineering relocates to Block C:
  BEFORE (2NF): Must update DeptLoc in rows for E1 AND E2 (two rows).
  AFTER  (3NF): UPDATE DEPARTMENT_3NF SET DeptLoc = 'Block C' WHERE DeptID = 'D1'
                → ✅ ONE row updated. Single source of truth for dept data.

REDUNDANCY — Dept data repeated per employee:
  BEFORE (2NF): D1's data appears once for Alice AND once for Bob.
  AFTER  (3NF): D1's data appears ONCE in DEPARTMENT_3NF.
                EMPLOYEE_3NF just stores the FK (DeptID) pointer.
```

### 3NF FD Verification

```sql
EMPLOYEE_3NF(EmpID, EmpName, DeptID):
  EmpID → EmpName  : Is EmpID a superkey? YES ✅
  EmpID → DeptID   : Is EmpID a superkey? YES ✅
  → NO 3NF violations. ✓

DEPARTMENT_3NF(DeptID, DeptName, DeptLoc):
  DeptID → DeptName : Is DeptID a superkey? YES ✅
  DeptID → DeptLoc  : Is DeptID a superkey? YES ✅
  → NO 3NF violations. ✓

PROJECT_3NF(ProjID, ProjName, ProjBudget):
  ProjID → ProjName   : Is ProjID a superkey? YES ✅
  ProjID → ProjBudget : Is ProjID a superkey? YES ✅
  → NO 3NF violations. ✓

WORKS_ON_3NF(EmpID, ProjID, HrsWorked):
  (EmpID, ProjID) → HrsWorked : Is (EmpID, ProjID) a superkey? YES ✅
  → NO 3NF violations. ✓
```

**Our main example is now also in BCNF!** (Because all determinants are superkeys in every table.)

To demonstrate a **3NF → BCNF** distinction, we need a scenario with multiple overlapping candidate keys — see 3.4.

### ❌ What 3NF May Not Solve (The Edge Case)

3NF is satisfied even when:
- X → A, where **A is a prime attribute** and **X is NOT a superkey**

This is the "exception clause" in the 3NF definition that BCNF removes. This edge case only arises when there are **multiple overlapping candidate keys** (i.e., candidate keys that share some attributes).

**→ Solution for this edge case: BCNF**

---

## 3.4 BOYCE-CODD NORMAL FORM (BCNF)

### Formal Definition
A relation R is in **BCNF** if and only if:
1. It is in **3NF**, AND
2. For **every** non-trivial functional dependency X → Y in R, **X must be a superkey** — no exceptions

**Comparing 3NF and BCNF:**

```
3NF allows: X → A  where A is prime, even if X is not a superkey
BCNF says:  X MUST be a superkey — full stop, no exceptions
```

> Every BCNF relation is in 3NF, but NOT every 3NF relation is in BCNF.
> BCNF differs from 3NF ONLY when there are multiple candidate keys that overlap (share prime attributes).

### New Dedicated Example: COURSE\_TEACHER\_STUDENT (CTS)

**Business Rules:**
1. A student enrolled in a course is taught by exactly **one teacher**
2. Each teacher teaches **only one course** (but a course can have many teachers)
3. A course can be taught by **multiple teachers**

**Table: CTS(StudentID, CourseID, TeacherID)**

| StudentID | CourseID | TeacherID |
|---|---|---|
| S1 | DBMS | T1 |
| S1 | OS | T3 |
| S2 | DBMS | T2 |
| S2 | OS | T3 |
| S3 | DBMS | T1 |
| S3 | Math | T4 |

**Functional Dependencies:**

```
FD1: (StudentID, CourseID) → TeacherID
     [A student in a course has exactly one teacher]

FD2: (StudentID, TeacherID) → CourseID
     [A student takes exactly one course from a given teacher]

FD3: TeacherID → CourseID
     [Each teacher teaches only one course — this is the KEY FD]
```

**Candidate Keys:**
```
CK1: {StudentID, CourseID}   — derived from FD1
CK2: {StudentID, TeacherID}  — derived from FD2
```

**Prime Attributes:** StudentID, CourseID, TeacherID — ALL attributes are prime! (Each belongs to at least one CK)

### 3NF Check for CTS

```
Checking FD3: TeacherID → CourseID
  3NF requires: Is TeacherID a superkey?   NO ❌
                OR is CourseID prime?       YES ✅ (CourseID ∈ CK1)
  → 3NF exception clause saves it → CTS IS IN 3NF ✓

So CTS is in 3NF. But is it problem-free? NO!
```

**Problems Still Present in CTS (despite being in 3NF):**

Because `TeacherID → CourseID`, the teacher-course fact is redundant:
```
T1 teaches DBMS — this appears in ROWS 1 AND 5 (wherever T1 appears)
T3 teaches OS   — this appears in ROWS 2 AND 4 (wherever T3 appears)
T2 teaches DBMS — appears in ROW 3

UPDATE ANOMALY: If T1 switches from DBMS to AI → must update ALL rows with T1
INSERTION ANOMALY: Can't record "T5 teaches Networks" until a student takes it
REDUNDANCY: Teacher-course assignment stored multiple times
```

### BCNF Check for CTS

```
Checking FD3: TeacherID → CourseID
  BCNF requires: Is TeacherID a superkey?   NO ❌
  → BCNF is VIOLATED! (No exception clause in BCNF)
  → The fact "TeacherID determines CourseID" but TeacherID alone doesn't
    uniquely identify rows in CTS.
```

### Achieving BCNF: Decomposing CTS

**Rule:** For the violating FD (TeacherID → CourseID), create a table with TeacherID as PK. Remaining attributes form another table.

```
Decompose CTS(StudentID, CourseID, TeacherID) using FD3: TeacherID → CourseID

Table 1: TEACHER_COURSE(TeacherID, CourseID)   ← from the violating FD
Table 2: STUDENT_TEACHER(StudentID, TeacherID) ← remaining attributes
```

---

**Table 1: TEACHER\_COURSE\_BCNF**

| **TeacherID** (PK) | CourseID |
|---|---|
| T1 | DBMS |
| T2 | DBMS |
| T3 | OS |
| T4 | Math |

**BCNF Check:** TeacherID → CourseID. Is TeacherID a superkey? YES ✅

---

**Table 2: STUDENT\_TEACHER\_BCNF**

| **StudentID** | **TeacherID** (FK) |
|---|---|
| S1 | T1 |
| S1 | T3 |
| S2 | T2 |
| S2 | T3 |
| S3 | T1 |
| S3 | T4 |

**PK: (StudentID, TeacherID)**

**BCNF Check:** (StudentID, TeacherID) is the PK = superkey. Only FD is the full key → trivially satisfies BCNF. ✅

---

**BCNF Advantages demonstrated:**

```
UPDATE ANOMALY fixed:
  T1 switches from DBMS to AI → UPDATE TEACHER_COURSE SET CourseID='AI' WHERE TeacherID='T1'
  → ONE row updated ✅

INSERTION ANOMALY fixed:
  Record "T5 teaches Networks" → INSERT INTO TEACHER_COURSE VALUES ('T5', 'Networks')
  → Works without any student enrollment ✅

REDUNDANCY fixed:
  T1→DBMS stored ONCE. No matter how many students take DBMS with T1, 
  the teacher-course fact is stored in a single row in TEACHER_COURSE ✅
```

---

### ⚠️ The Critical BCNF Trade-off: Dependency NOT Preserved

The original FD1: **(StudentID, CourseID) → TeacherID** is LOST in the decomposition!

```
To check whether "student S1 in DBMS is taught by T1 (and not T2)":
  TEACHER_COURSE has only TeacherID → CourseID (doesn't involve StudentID)
  STUDENT_TEACHER has only StudentID, TeacherID (doesn't have CourseID)

→ You CANNOT verify FD1 without JOINING both tables.
→ The dependency (StudentID, CourseID) → TeacherID is NOT preserved!
```

This is the fundamental 3NF vs BCNF trade-off:

| Property | 3NF | BCNF |
|---|---|---|
| **Lossless join** | ✅ Always | ✅ Always |
| **Dependency preserving** | ✅ Always | ❌ NOT always |
| **Eliminates ALL FD-based redundancy** | ❌ May leave some | ✅ Yes |

### ❌ What BCNF Does NOT Solve

BCNF handles ALL functional dependency-based anomalies. However:
- When attributes have **multiple independent values** for the same key (multi-valued dependencies)
- When the problem isn't a functional dependency at all, but independent multiplicity
- BCNF tables can still have significant redundancy due to MVDs

**→ Solution: 4NF**

---

## 3.5 FOURTH NORMAL FORM (4NF)

### New Concept: Multi-Valued Dependency (MVD)

**Definition:**
In a relation R with attributes A, B, C:
X **multi-value determines** Y (written **X →→ Y**) if for each value of X, the set of Y-values associated with it is **independent** of the other attributes Z in the relation.

**Intuitive meaning:**
> X →→ Y means: the set of Y values for a given X has nothing to do with Z values. X independently determines a SET of Y values and independently a SET of Z values.

### MVD Example: EMPLOYEE\_SKILL\_LANGUAGE

An employee has multiple skills and speaks multiple languages. Skills and languages are **completely independent** of each other.

```
Business rules:
  - An employee can have multiple skills
  - An employee can speak multiple languages
  - Whether an employee has a skill has NO dependency on which languages they speak
  - These are two INDEPENDENT facts about the same employee
```

**Table: ESL(EmpID, Skill, Language) — in BCNF but NOT in 4NF**

| EmpID | Skill | Language |
|---|---|---|
| E1 | Java | English |
| E1 | Java | French |
| E1 | Python | English |
| E1 | Python | French |
| E2 | SQL | English |
| E2 | SQL | German |

**MVDs Present:**
```
E1 →→ Skill     (E1's skills = {Java, Python} regardless of languages)
E1 →→ Language  (E1's languages = {English, French} regardless of skills)
```

**Why is this a problem?**

```
REDUNDANCY: The fact "E1 knows Java" appears TWICE (once per language).
            The fact "E1 speaks French" appears TWICE (once per skill).

Adding a new skill "C++" for E1:
  Must insert: (E1, C++, English) AND (E1, C++, French)  → 2 rows for 1 new fact

Adding a new language "Spanish" for E1:
  Must insert: (E1, Java, Spanish) AND (E1, Python, Spanish) → 2 rows for 1 new fact

The number of rows = |skills| × |languages| — combinatorial explosion!
If E1 has 5 skills and 4 languages = 20 rows, all just repeating combinations
```

**BCNF check for ESL:**

```
Candidate Key: (EmpID, Skill, Language) — ALL attributes (no non-trivial FDs)
There are no non-trivial FDs where the LHS is not a superkey.
→ ESL IS IN BCNF ✓

Yet it clearly has MASSIVE redundancy! → BCNF is insufficient!
```

### 4NF Formal Definition

A relation R is in **4NF** if and only if:
1. It is in **BCNF**, AND
2. For every **non-trivial multi-valued dependency** X →→ Y in R, **X must be a superkey**

**Non-trivial MVD:** X →→ Y is non-trivial if Y ⊄ X AND X ∪ Y ≠ all attributes of R.

### Achieving 4NF: Decompose on Each MVD Separately

**Rule:** For each independent MVD X →→ Y, create a separate binary table (X, Y).

```
MVD1: EmpID →→ Skill     → Create EMP_SKILL(EmpID, Skill)
MVD2: EmpID →→ Language  → Create EMP_LANGUAGE(EmpID, Language)
```

---

**Table 1: EMP\_SKILL\_4NF**

| **EmpID** | **Skill** |
|---|---|
| E1 | Java |
| E1 | Python |
| E2 | SQL |

**PK: (EmpID, Skill)**

---

**Table 2: EMP\_LANGUAGE\_4NF**

| **EmpID** | **Language** |
|---|---|
| E1 | English |
| E1 | French |
| E2 | English |
| E2 | German |

**PK: (EmpID, Language)**

---

### How 4NF Fixes MVD Problems

```
Adding new skill "C++" for E1:
  BEFORE (BCNF): INSERT (E1, C++, English) AND (E1, C++, French) — 2 rows!
  AFTER  (4NF):  INSERT INTO EMP_SKILL VALUES (E1, C++)          — 1 row ✅

Adding new language "Spanish" for E1:
  BEFORE (BCNF): INSERT (E1, Java, Spanish) AND (E1, Python, Spanish) — 2 rows!
  AFTER  (4NF):  INSERT INTO EMP_LANGUAGE VALUES (E1, Spanish)        — 1 row ✅

Removing skill "Python" for E1:
  BEFORE (BCNF): DELETE WHERE EmpID='E1' AND Skill='Python' — deletes 2 rows
  AFTER  (4NF):  DELETE FROM EMP_SKILL WHERE EmpID='E1' AND Skill='Python' — 1 row ✅

No more coupling between independent facts. Each table stores ONE independent 
multi-valued fact about an entity.
```

### Reconstructing Original Data (Lossless)
```sql
-- Get all combinations (as originally stored in ESL) via NATURAL JOIN equivalent:
SELECT s.EmpID, s.Skill, l.Language
FROM EMP_SKILL_4NF s
JOIN EMP_LANGUAGE_4NF l ON s.EmpID = l.EmpID;
-- Returns exactly the original ESL data — lossless decomposition ✅
```

### ❌ What 4NF Does NOT Solve

4NF handles multi-valued dependencies. What remains are cases of:
- **Join dependencies** — situations where a relation cannot be losslessly decomposed into two projections but CAN be decomposed into three or more
- These are extremely rare in practice

**→ Solution: 5NF**

---

## 3.6 FIFTH NORMAL FORM (5NF) — Project-Join Normal Form

### New Concept: Join Dependency

A relation R has a **Join Dependency (JD)** \*(R1, R2, ..., Rn)\* if R can be losslessly reconstructed by natural joining R1, R2, ..., Rn (which are projections of R onto those attribute subsets).

> Every relation has trivial JDs (into itself). 5NF is about **non-trivial** JDs.

### 5NF Formal Definition

A relation R is in **5NF** if and only if:
1. It is in **4NF**, AND
2. Every non-trivial join dependency in R is **implied by the superkeys** of R

### Example: SUPPLIER\_PART\_PROJECT (SPJ)

**Business Rules (the cyclical constraint):**
A supplier S supplies a part P to a project J **only if ALL three conditions hold**:
1. Supplier S supplies part P (S-P relationship exists)
2. Project J uses part P (P-J relationship exists)
3. Supplier S works with project J (S-J relationship exists)

This is NOT representable as a pairwise binary relationship — all three must be checked together.

**Table: SPJ(SupplierID, PartID, ProjectID)**

| SupplierID | PartID | ProjectID |
|---|---|---|
| S1 | P1 | J1 |
| S1 | P1 | J2 |
| S1 | P2 | J1 |
| S2 | P1 | J1 |

**This table has a Join Dependency:**
```
SPJ = π_{S,P}(SPJ) ⋈ π_{P,J}(SPJ) ⋈ π_{S,J}(SPJ)

In English: SPJ can be perfectly reconstructed by joining
  - (S1,P1), (S1,P2), (S2,P1)         [Supplier-Part pairs]
  - (P1,J1), (P1,J2), (P2,J1)         [Part-Project pairs]
  - (S1,J1), (S1,J2), (S2,J1)         [Supplier-Project pairs]
```

If this JD is not implied by the candidate key ({SupplierID, PartID, ProjectID} = entire tuple), then 5NF is violated.

### Achieving 5NF

```sql
-- Table 1: SUPPLIER_PART_5NF
(S1, P1), (S1, P2), (S2, P1)

-- Table 2: PART_PROJECT_5NF
(P1, J1), (P1, J2), (P2, J1)

-- Table 3: SUPPLIER_PROJECT_5NF
(S1, J1), (S1, J2), (S2, J1)
```

Now adding/removing relationships is done by modifying individual binary tables.

> **In practice:** 5NF violations are rare and mostly of academic interest. Real-world databases almost never explicitly target 5NF. Most practical design stops at **3NF or BCNF**.

## 4.2 Final 3NF Schema with SQL

```sql
-- 1. DEPARTMENT (independent entity)
CREATE TABLE Department (
    DeptID      VARCHAR(5)    PRIMARY KEY,
    DeptName    VARCHAR(100)  NOT NULL UNIQUE,
    DeptLoc     VARCHAR(100)
);

-- 2. EMPLOYEE (depends on Department via FK)
CREATE TABLE Employee (
    EmpID    VARCHAR(5)    PRIMARY KEY,
    EmpName  VARCHAR(100)  NOT NULL,
    DeptID   VARCHAR(5),
    FOREIGN KEY (DeptID) REFERENCES Department(DeptID)
        ON UPDATE CASCADE
        ON DELETE SET NULL
);

-- 3. EMP_PHONE (multi-valued attribute in its own table)
CREATE TABLE EmpPhone (
    EmpID   VARCHAR(5)   NOT NULL,
    Phone   VARCHAR(15)  NOT NULL,
    PRIMARY KEY (EmpID, Phone),
    FOREIGN KEY (EmpID) REFERENCES Employee(EmpID)
        ON DELETE CASCADE
);

-- 4. PROJECT (independent entity)
CREATE TABLE Project (
    ProjID      VARCHAR(5)    PRIMARY KEY,
    ProjName    VARCHAR(100)  NOT NULL,
    ProjBudget  DECIMAL(12,2)
);

-- 5. WORKS_ON (relationship table — junction)
CREATE TABLE WorksOn (
    EmpID       VARCHAR(5)  NOT NULL,
    ProjID      VARCHAR(5)  NOT NULL,
    HrsWorked   INT         NOT NULL DEFAULT 0,
    PRIMARY KEY (EmpID, ProjID),
    FOREIGN KEY (EmpID)  REFERENCES Employee(EmpID) ON DELETE CASCADE,
    FOREIGN KEY (ProjID) REFERENCES Project(ProjID)  ON DELETE RESTRICT
);
```

## 4.4 Anomaly Resolution by Normal Form

| Anomaly | Not Fixed Until... | Mechanism |
|---|---|---|
| Non-atomic / multi-valued cells | **1NF** | Separate repeated values into their own table |
| Partial dependency on composite key | **2NF** | Separate partially-dependent attrs into their own table |
| Insertion anomaly (from partial dep) | **2NF** | Entity data no longer hostage to relationship |
| Update anomaly (from partial dep) | **2NF** | Single source of truth for each attribute |
| Deletion anomaly (from partial dep) | **2NF** | Entities stored independently from relationships |
| Transitive dependency | **3NF** | Remove non-key intermediaries to their own table |
| Insertion anomaly (from transitive dep) | **3NF** | Transitively related entity gains independence |
| Update anomaly (from transitive dep) | **3NF** | Single row stores transitively dependent data |
| Deletion anomaly (from transitive dep) | **3NF** | Independent entity table survives parent deletion |
| Redundancy from prime-attr FDs (non-superkey determinant) | **BCNF** | Every determinant must be a superkey, no exceptions |
| Redundancy from independent multi-valued facts | **4NF** | Independent MVDs separated into binary tables |
| Redundancy from join dependencies | **5NF** | Non-key JDs decomposed into multiple binary tables |

## 4.5 Formal Definitions Side-by-Side

| NF | Formal Condition in One Line |
|---|---|
| **1NF** | All attribute domains are atomic; no multi-valued or composite attributes |
| **2NF** | 1NF + no non-prime attribute partially depends on any candidate key |
| **3NF** | 1NF + for every non-trivial FD X→A: X is a superkey OR A is prime |
| **BCNF** | 1NF + for every non-trivial FD X→A: X MUST be a superkey (no exceptions) |
| **4NF** | BCNF + for every non-trivial MVD X→→Y: X must be a superkey |
| **5NF** | 4NF + every non-trivial join dependency is implied by the superkeys |

## 4.6 Detailed Pairwise Comparisons

### 1NF vs 2NF

| Aspect | 1NF | 2NF |
|---|---|---|
| **Main concern** | Atomicity of values | Structure of functional dependencies |
| **Problem solved** | Non-atomic cells (lists, arrays in cells) | Partial FDs on composite keys |
| **Relevant when** | Always | ONLY when composite PK exists |
| **Key question** | "Is each cell a single value?" | "Does each non-prime attr need the FULL composite key?" |
| **Violation example** | Phone: "9876, 8765" in one cell | EmpName depends only on EmpID within (EmpID, ProjID) key |
| **Fix technique** | Separate multi-valued attr into own table | Separate partially-dependent attrs into own table by their determining key part |

### 2NF vs 3NF

| Aspect | 2NF | 3NF |
|---|---|---|
| **Main concern** | Dependency on part of composite key | Non-key attributes determining other non-key attrs |
| **Dependency type** | A ← (subset of CK) ← full CK | A ← Z ← CK where Z is non-key |
| **Chain structure** | Key → (partial key) → attribute | Key → (non-key) → attribute |
| **Violation example** | EmpName ← EmpID ⊂ {EmpID, ProjID} | DeptName ← DeptID ← EmpID |
| **Test** | "Can any part of the composite key alone determine a non-prime attr?" | "Does any non-key column determine another non-key column?" |
| **Requires composite key?** | YES — only relevant for composite PKs | NO — can occur even with single-col PK if there are non-key intermediaries |

### 3NF vs BCNF — The Most Critical Comparison

| Aspect                      | 3NF                                           | BCNF                                            |     |
| --------------------------- | --------------------------------------------- | ----------------------------------------------- | --- |
| **Exception clause**        | X→A allowed if A is prime                     | NO exceptions — X must always be a superkey     |     |
| **When they differ**        | Only when multiple candidate keys overlap     | Same — this is exactly the problematic scenario |     |
| **Redundancy eliminated**   | Most, but not all FD-based                    | ALL FD-based redundancy eliminated              |     |
| **Lossless decomposition**  | ✅ Always guaranteed                           | ✅ Always guaranteed                             |     |
| **Dependency preservation** | ✅ Always guaranteed                           | ❌ May NOT preserve all FDs                      |     |
| **Practical preference**    | ⭐ **Used in most real systems**               | Preferred when DP not critical                  |     |
| **Theoretic strength**      | Weaker                                        | Stronger                                        |     |
| **When to prefer 3NF**      | When you cannot afford to check FDs via joins | Almost always in practice                       |     |
| **When to prefer BCNF**     | When anomaly-free design outweighs DP concern | Read-heavy, write-light systems                 |     |

### BCNF vs 4NF

| Aspect | BCNF | 4NF |
|---|---|---|
| **Dependency type handled** | Functional dependencies (X → Y, one value) | Multi-valued dependencies (X →→ Y, a SET of values) |
| **Problem type** | Redundancy from FDs where LHS isn't superkey | Redundancy from independent multi-valued attributes |
| **Example** | TeacherID → CourseID (one course per teacher) | EmpID →→ Skill (multiple independent skills) |
| **Row structure** | Non-superkey determines single value in same row | Non-superkey independently determines sets of values in multiple rows |
| **Combinatorial explosion** | Not applicable | YES — rows = product of two independent sets |
| **Check using** | Functional dependency analysis | Multi-valued dependency analysis |

## 4.7 What Each Normal Form "Sees" and "Fixes"

```
TYPE OF PROBLEM           │ CAUGHT BY │ FIXED BY
──────────────────────────┼───────────┼─────────
Non-atomic cell value     │   1NF     │   1NF
Partial FD (composite key)│   2NF     │   2NF
Transitive FD             │   3NF     │   3NF
Prime-attr FD non-superkey│   BCNF    │   BCNF
Multi-valued dependency   │   4NF     │   4NF
Join dependency           │   5NF     │   5NF
──────────────────────────┴───────────┴─────────
FD = Functional Dependency
MVD = Multi-Valued Dependency
JD = Join Dependency
```

## 4.8 Normalization: Practical Recommendation Guide

| System Type | Recommended NF | Reason |
|---|---|---|
| **OLTP (transactional)** | 3NF | Best balance of integrity and performance |
| **Financial / Medical (critical)** | BCNF | Higher write integrity required |
| **Data Warehouse (OLAP)** | 1NF–2NF (intentionally denormalized!) | Read performance >> write consistency |
| **Reporting systems** | 2NF (star schema) | Pre-joined/aggregated data for fast reports |
| **General web applications** | 3NF | Industry standard |
| **Systems with multi-valued attributes** | 4NF | Avoid MVD combinatorial redundancy |
| **Complex constraint systems** | 5NF | Only when real join dependencies identified |

---

## 4.9 When to INTENTIONALLY Denormalize

Denormalization = **purposeful introduction of redundancy for performance gains**.

```
Normalize first → identify bottlenecks → selectively denormalize with full awareness.
NEVER start with denormalization.
```

| Scenario | Denormalization Strategy | Trade-off |
|---|---|---|
| Heavily read, rarely written | Pre-join tables; store redundant cols | Faster reads; slower writes; risk of inconsistency |
| Complex multi-table reports | Materialized views / summary tables | Pre-computed results; stale data risk |
| High-traffic API responses | Add redundant denormalized columns | Fewer JOINs per request; write sync needed |
| Data warehouses (OLAP) | Star schema (fact + dimension tables) | Faster analytical queries; intentional redundancy |
| Mobile/offline databases | Flat denormalized local copy | Works offline; must sync carefully |

## 4.10 Complete Summary: The One-Page Visual

```
┌──────────────────────────────────────────────────────────────────────┐
│                  NORMALIZATION AT A GLANCE                           │
├─────────┬──────────────────────┬─────────────────────────────────────┤
│   NF    │  Problem It Solves   │  Key Rule / Test                    │
├─────────┼──────────────────────┼─────────────────────────────────────┤
│  1NF    │ Non-atomic values    │ Every cell = exactly one value      │
│         │ Repeating groups     │ No lists/arrays/sets in a cell      │
├─────────┼──────────────────────┼─────────────────────────────────────┤
│  2NF    │ Partial dependencies │ Every non-prime attr depends on     │
│         │ (composite key only) │ the ENTIRE candidate key            │
├─────────┼──────────────────────┼─────────────────────────────────────┤
│  3NF    │ Transitive           │ No non-prime attr depends on        │
│         │ dependencies         │ another non-prime attr              │
│         │                      │ (non-key → non-key not allowed)     │
├─────────┼──────────────────────┼─────────────────────────────────────┤
│  BCNF   │ Prime attribute FDs  │ For EVERY non-trivial FD X→Y:       │
│         │ (stricter 3NF)       │ X MUST be a superkey (no excepts.)  │
│         │                      │ ⚠️May lose dependency preservation  │
├─────────┼──────────────────────┼─────────────────────────────────────┤
│  4NF    │ Multi-valued         │ For every non-trivial MVD X→→Y:     │
│         │ dependencies         │ X must be a superkey                │
│         │                      │ Separate independent MVDs into      │
│         │                      │ their own binary tables             │
├─────────┼──────────────────────┼─────────────────────────────────────┤
│  5NF    │ Join dependencies    │ Every non-trivial JD implied by     │
│         │ (rare in practice)   │ superkeys of the relation           │
└─────────┴──────────────────────┴─────────────────────────────────────┘

Inclusion: 5NF ⊂ 4NF ⊂ BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF ⊂ All Relations

In practice: Aim for 3NF (or BCNF if dependency preservation allows).
             4NF and 5NF address edge cases identified through analysis.
             Denormalize only after profiling shows performance need.
```

---

> **The Essential Takeaway:**
>
> Normalization is not about mechanically chasing the highest normal form — it is a **deliberate design philosophy**:
>
> - **1NF** enforces the relational model's most basic rule: atomic values
> - **2NF** ensures that composite keys don't create partial-dependency anomalies
> - **3NF** ensures entities are independent — departments, projects, employees each have their own tables
> - **BCNF** removes the last loophole in 3NF at the cost of possible dependency-preservation loss
> - **4NF** addresses independent multi-valued facts that 4NF sees but FD-based NFs cannot
> - **5NF** is the theoretical endpoint — rarely targeted explicitly
>
> **In real-world systems: design to 3NF by default. Upgrade to BCNF where dependency preservation permits. Denormalize with explicit measurement-driven justification.**
