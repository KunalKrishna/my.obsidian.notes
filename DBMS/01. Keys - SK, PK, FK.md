# Keys in Relational Database Management System (RDBMS)
## Comprehensive Notes

---
# PART 1 — FOUNDATION & CONTEXT
---
## 1.1 What is a "Key"?

A **Key** is one or more attribute(s) (column/columns) in a relation (table) that serve a specific role in:
- **Uniquely identifying** tuples (rows) within a table
- **Establishing relationships** between tables
- **Enforcing data integrity** constraints (uniqueness, non-nullability, referential integrity)
- **Optimizing data retrieval** through indexing

Without keys, a relational database would have no reliable mechanism to:
- Distinguish one row from another
- Link related data across tables
- Prevent duplicate or orphaned records
---
## 1.2 The Key Hierarchy (Big Picture)

Before diving into individual key types, understanding their logical hierarchy prevents confusion:

```css
All possible combinations of attributes
            │
            ▼
      ┌──────────────┐
      │  SUPERKEY    │  → Any set of attributes that uniquely identifies a row
      │              │    (may contain redundant attributes)
      └──────┬───────┘
             │ (minimize — remove redundant attributes)
             ▼
      ┌──────────────┐
      │ CANDIDATE KEY│  → Minimal superkey; no subset of it is also a superkey
      │              │    A table can have MULTIPLE candidate keys
      └──────┬───────┘
             │ (DBA chooses ONE among candidates)
             ▼
      ┌──────────────┐
      │ PRIMARY KEY  │  → The chosen candidate key; main identifier of the table
      │(Simple or    │    Simple (1 column) or Composite (2+ columns)
      │ Composite)   │
      └──────────────┘
             │
             │ (referenced by)
             ▼
      ┌──────────────┐
      │ FOREIGN KEY  │  → Attribute(s) in another table that reference
      │              │    the PK/candidate key of this table
      └──────────────┘
```

---
## 1.3 Core Relational Integrity Rules (Context for Keys)

| Integrity Rule | Description | Enforced By |
|---|---|---|
| **Entity Integrity** | Primary key columns must be unique and NOT NULL | Primary Key constraint |
| **Referential Integrity** | FK values must match an existing PK value in the referenced table (or be NULL) | Foreign Key constraint |
| **Domain Integrity** | Values must belong to valid domain (type, range, format) | Data types, CHECK constraints |

# PART 2 — TYPES OF KEYS (DETAILED)

## 2.1 CANDIDATE KEY

### Definition
> A **Candidate Key** is a **minimal set of one or more attributes** that can **uniquely identify every tuple** in a relation. It is "minimal" meaning no attribute can be removed from the set without losing the uniqueness property.

### Key Properties

| Property | Description |
|---|---|
| **Uniqueness** | Every row must have a distinct value for the candidate key |
| **Minimality** | No proper subset of the candidate key can also uniquely identify rows |
| **Non-nullability** | Conceptually, a candidate key should not contain NULL values |
| **Multiplicity** | A table can have **more than one** candidate key |
| **Eligibility** | Every candidate key is eligible to become the primary key |
### Conceptual Analogy
Think of candidate keys as *all applicants for the role of "table identifier."* All are qualified (unique + minimal), but only one will be selected (becomes Primary Key), while the others remain available as alternate identifiers.
### Example
Consider a **Student** table:
```sql
Student Table
┌────────────┬──────────────┬─────────────────────────┬──────────────────┐
│ student_id │     name     │           ssn           │      email       │
├────────────┼──────────────┼─────────────────────────┼──────────────────┤
│    101     │  Alice Roy   │    123-45-6789          │alice@univ.edu    │
│    102     │  Bob Singh   │    987-65-4321          │bob@univ.edu      │
│    103     │  Carol Das   │    456-78-9012          │carol@univ.edu    │
└────────────┴──────────────┴─────────────────────────┴──────────────────┘
```
**Identifying candidate keys:**
- `student_id` → each value is unique ✅ | minimal (single column) ✅ → **Candidate Key**
- `ssn` → each Social Security Number is globally unique ✅ | minimal ✅ → **Candidate Key**
- `email` → each email is unique ✅ | minimal ✅ → **Candidate Key**
- `name` → names can repeat ❌ → **NOT a candidate key**
- `{student_id, ssn}` → unique ✅ but NOT minimal (removing either still gives uniqueness) ❌ → **Superkey, NOT a Candidate Key**

**Candidate Keys for this table: {student_id}, {ssn}, {email}**

### SQL Enforcement of Candidate Keys
```sql
CREATE TABLE Student (
    student_id  INT           NOT NULL,     -- Candidate Key 1
    ssn         CHAR(11)      NOT NULL,     -- Candidate Key 2
    email       VARCHAR(100)  NOT NULL,     -- Candidate Key 3
    name        VARCHAR(100),

    -- One becomes the Primary Key:
    PRIMARY KEY (student_id),

    -- Others are enforced as UNIQUE + NOT NULL:
    UNIQUE (ssn),
    UNIQUE (email)
);
```

> 💡 **Key Insight:** In SQL, candidate keys that are not chosen as the primary key are enforced using **`UNIQUE NOT NULL`** constraints. UNIQUE alone allows NULLs (in most DBMS), so `NOT NULL` must be added explicitly to truly enforce candidate key semantics.
### Significance of Candidate Keys
1. **Foundation for normalization**: Functional dependencies based on candidate keys guide normalization (BCNF, 3NF)
2. **Design flexibility**: DBA can choose the most efficient or meaningful candidate key as PK
3. **Alternate access paths**: Other candidate keys serve as efficient lookup columns (via UNIQUE indexes)
4. **Theoretical completeness**: They represent the complete set of minimal identifiers in logical design

## 2.2 PRIMARY KEY (Simple / Single-Column)

### Definition
> A **Primary Key** is the **one candidate key officially designated** as the main, permanent identifier for rows in a table. It is the backbone of the table's identity.

### Key Properties

| Property | Description |
|---|---|
| **Uniqueness** | Every row must have a distinct PK value — no duplicates allowed |
| **Non-nullability** | PK columns can NEVER be NULL (Entity Integrity) |
| **Singularity** | Only **ONE** Primary Key constraint is allowed per table |
| **Stability** | PK values should be stable — avoid values that change frequently |
| **Referenced** | PKs are the target of Foreign Key constraints in other tables |
| **Indexed** | DBMS automatically creates a unique index (usually clustered) on the PK |
### Types of Primary Keys (by nature)

| Type              | Description                                    | Example                  |
| ----------------- | ---------------------------------------------- | ------------------------ |
| **Natural Key**   | Uses a real-world attribute already meaningful | SSN, ISBN, email         |
| **Surrogate Key** | System-generated, has no real-world meaning    | Auto-increment INT, UUID |

**Natural Key Example:**
```sql
CREATE TABLE Book (
    isbn    CHAR(13)     PRIMARY KEY,    -- ISBN is globally unique
    title   VARCHAR(200),
    author  VARCHAR(100)
);
```

**Surrogate Key Example (most common in practice):**
```sql
CREATE TABLE Student (
    student_id  INT          PRIMARY KEY AUTO_INCREMENT,  -- surrogate
    name        VARCHAR(100) NOT NULL,
    ssn         CHAR(11)     UNIQUE NOT NULL,
    email       VARCHAR(100) UNIQUE NOT NULL
);
```
### Why Choose Surrogate Over Natural Keys?

| Criterion | Natural Key | Surrogate Key |
|---|---|---|
| **Meaning** | Inherently meaningful | No inherent meaning |
| **Stability** | Can change (email, SSN) | Never changes |
| **Size** | Often large (string) | Small (INT, UUID) |
| **Privacy** | May expose sensitive info (SSN) | No sensitive data |
| **Join efficiency** | Slower (wide keys) | Faster (small integer) |
| **Best for** | Lookup/reference tables | General entity tables |
### Simple Primary Key — Detailed Example

**Schema:**
```sql
CREATE TABLE Department (
    dept_id   INT          PRIMARY KEY AUTO_INCREMENT,
    dept_name VARCHAR(100) NOT NULL UNIQUE,
    location  VARCHAR(100)
);

CREATE TABLE Employee (
    emp_id    INT          PRIMARY KEY AUTO_INCREMENT,
    emp_name  VARCHAR(100) NOT NULL,
    salary    DECIMAL(10,2),
    dept_id   INT,
    FOREIGN KEY (dept_id) REFERENCES Department(dept_id)
);
```

**Data:**
```postgresql
Department
┌─────────┬───────────────┬──────────────┐
│ dept_id │   dept_name   │   location   │
├─────────┼───────────────┼──────────────┤
│    1    │   Engineering │   Building A │
│    2    │   Marketing   │   Building B │
│    3    │   HR          │   Building C │
└─────────┴───────────────┴──────────────┘

Employee
┌────────┬────────────┬──────────┬─────────┐
│ emp_id │  emp_name  │  salary  │ dept_id │
├────────┼────────────┼──────────┼─────────┤
│   1    │  Alice     │ 75000.00 │    1    │
│   2    │  Bob       │ 65000.00 │    2    │
│   3    │  Carol     │ 80000.00 │    1    │
└────────┴────────────┴──────────┴─────────┘
```
### What Happens When PK Rules Are Violated?

```sql
-- Attempting to insert a duplicate PK value:
INSERT INTO Employee (emp_id, emp_name) VALUES (1, 'Dave');
-- ERROR: Duplicate entry '1' for key 'PRIMARY'

-- Attempting to insert a NULL PK value:
INSERT INTO Employee (emp_id, emp_name) VALUES (NULL, 'Eve');
-- ERROR: Column 'emp_id' cannot be null
```
### Significance of Primary Key
1. **Entity integrity**: Guarantees every row is distinctly identifiable
2. **Joining tables**: The primary key is the anchor for JOIN operations
3. **Target for foreign keys**: Other tables reference the PK to create relationships
4. **Indexing and performance**: Auto-indexing speeds up queries, updates, deletes
5. **Data quality**: Prevents phantom or duplicate entities

## 2.3 COMPOSITE PRIMARY KEY

### Definition
> A **Composite Primary Key** is a **Primary Key that consists of two or more columns** whose combination uniquely identifies a row. No single column alone is sufficient.

### When Is a Composite PK Needed?

A composite PK is the natural choice when:
1. **Many-to-many junction tables**: The combination of two FKs uniquely identifies the relationship
2. **Naturally composite identifiers**: E.g., a bank account transaction uniquely identified by (account_id + transaction_date + sequence_no)
3. **No natural single-column identifier exists** and adding a surrogate would be redundant
### Key Properties

| Property | Description |
|---|---|
| **Combined uniqueness** | The combination of all PK columns must be unique per row |
| **Individual columns** | Each column can repeat individually — only the combination must be unique |
| **Non-nullability** | ALL columns in the composite PK must be NOT NULL |
| **One PK per table** | Still counts as one PRIMARY KEY constraint (just multi-column) |
| **FK references** | Foreign keys pointing to this table must include ALL PK columns |

### Composite PK — Canonical Example: Many-to-Many

**Scenario:** Students enroll in Courses. One student can enroll in many courses; one course can have many students. The junction table `Enrollment` models this relationship.

```sql
CREATE TABLE Student (
    student_id  INT         PRIMARY KEY AUTO_INCREMENT,
    name        VARCHAR(100) NOT NULL
);

CREATE TABLE Course (
    course_id   INT         PRIMARY KEY AUTO_INCREMENT,
    title       VARCHAR(200) NOT NULL,
    credits     INT
);

CREATE TABLE Enrollment (
    student_id  INT          NOT NULL,
    course_id   INT          NOT NULL,
    semester    VARCHAR(10)  NOT NULL,    -- e.g., 'Fall2024'
    grade       CHAR(2),

    -- Composite Primary Key:
    PRIMARY KEY (student_id, course_id, semester),

    -- Foreign Keys:
    FOREIGN KEY (student_id) REFERENCES Student(student_id)
        ON DELETE CASCADE,
    FOREIGN KEY (course_id)  REFERENCES Course(course_id)
        ON DELETE RESTRICT
);
```

**Data in Enrollment:**
```
Enrollment
┌────────────┬───────────┬──────────┬───────┐
│ student_id │ course_id │ semester │ grade │
├────────────┼───────────┼──────────┼───────┤
│     1      │    101    │ Fall2024 │  A    │  ← unique combo ✅
│     1      │    102    │ Fall2024 │  B+   │  ← unique combo ✅
│     2      │    101    │ Fall2024 │  A-   │  ← unique combo ✅
│     1      │    101    │ Spr2025  │  B    │  ← unique combo ✅ (diff semester)
│     1      │    101    │ Fall2024 │  A    │  ← DUPLICATE ❌ (would be rejected)
└────────────┴───────────┴──────────┴───────┘
```

**Notice:** student_id=1 repeats, course_id=101 repeats — individually they repeat. Only the combination of all three must be unique.

### Second Example: Order Line Items

```sql
CREATE TABLE Orders (
    order_id    INT     PRIMARY KEY AUTO_INCREMENT,
    order_date  DATE    NOT NULL,
    customer_id INT     NOT NULL
);

CREATE TABLE OrderItem (
    order_id    INT     NOT NULL,
    item_no     INT     NOT NULL,     -- Line number within the order
    product_id  INT     NOT NULL,
    quantity    INT     NOT NULL,
    unit_price  DECIMAL(10,2) NOT NULL,

    PRIMARY KEY (order_id, item_no),  -- Composite PK

    FOREIGN KEY (order_id)   REFERENCES Orders(order_id) ON DELETE CASCADE,
    FOREIGN KEY (product_id) REFERENCES Product(product_id)
);
```

**Logic:** For Order #500, it can have Item #1, Item #2, Item #3. (500,1), (500,2), (500,3) are all unique combinations. Another order #501 can also have item #1 — (501,1) is a different combination.

### Composite PK — Advantages & Disadvantages

| Aspect | Advantage | Disadvantage |
|---|---|---|
| **Naturalness** | Reflects real-world composite identity | More complex to reason about |
| **Storage** | No extra surrogate column needed | Wider FK references (more storage) |
| **Data integrity** | Prevents duplicate relationships at DB level | Composite indexes are larger |
| **Join performance** | Fewer tables (no surrogate lookup) | Multi-column joins slightly slower |
| **FK references** | Semantically clear | All FK columns must be replicated in child |
| **Readability** | Self-documenting (columns explain relationship) | INSERT/UPDATE syntax is verbose |

### Composite PK vs Surrogate PK for Junction Tables

A design choice frequently debated:

**Option A — Composite PK (natural):**
```sql
CREATE TABLE Enrollment (
    student_id INT NOT NULL,
    course_id  INT NOT NULL,
    PRIMARY KEY (student_id, course_id)  -- Composite PK
);
```

**Option B — Surrogate PK + UNIQUE constraint:**
```sql
CREATE TABLE Enrollment (
    enrollment_id INT PRIMARY KEY AUTO_INCREMENT,  -- Surrogate PK
    student_id    INT NOT NULL,
    course_id     INT NOT NULL,
    UNIQUE (student_id, course_id)                 -- Uniqueness still enforced
);
```

**When to use which:**

| Use Composite PK When... | Use Surrogate PK When... |
|---|---|
| Other tables don't reference Enrollment rows | Other tables reference individual enrollment rows |
| The table is a pure junction table | The table has its own lifecycle / child tables |
| Keeping schema minimal is priority | Simplicity in ORM or application code is priority |
| No need for a row-level identifier beyond the combo | You need to refer to "this specific enrollment" |

## 2.4 FOREIGN KEY

### Definition
> A **Foreign Key** is an attribute (or set of attributes) in a **child table** whose values must correspond to values of a **Primary Key or Candidate Key in a parent table** (or be NULL if allowed). It enforces **Referential Integrity**.

### Key Properties

| Property | Description |
|---|---|
| **References parent key** | Must reference a PK or UNIQUE (NOT NULL) key in the parent table |
| **Referential integrity** | Child row cannot reference a non-existent parent row |
| **Nullability** | FK column CAN be NULL (meaning "no relationship" or unknown) unless declared NOT NULL |
| **Duplicates allowed** | Multiple child rows can reference the same parent row (models one-to-many) |
| **Multiple FKs per table** | A table can have several FK constraints |
| **Cascading actions** | DBA can define behavior when parent row is updated/deleted |
| **Self-referencing** | A table can have a FK that references its own PK (hierarchical data) |

### What Referential Integrity Means in Practice

```
Parent Table: Department (dept_id is PK)
┌─────────┬───────────────┐
│ dept_id │   dept_name   │
├─────────┼───────────────┤
│    1    │  Engineering  │
│    2    │  Marketing    │
└─────────┴───────────────┘

Child Table: Employee (dept_id is FK → Department.dept_id)
┌────────┬──────────┬─────────┐
│ emp_id │ emp_name │ dept_id │
├────────┼──────────┼─────────┤
│   1    │  Alice   │    1    │  → Valid: dept 1 exists ✅
│   2    │  Bob     │    2    │  → Valid: dept 2 exists ✅
│   3    │  Carol   │    9    │  → INVALID: dept 9 doesn't exist ❌
│   4    │  Dave    │  NULL   │  → Valid if FK column is nullable ✅
└────────┴──────────┴─────────┘
```

### Cascading Actions (ON DELETE / ON UPDATE)

When a parent row is modified or deleted, the DBMS needs instructions on what to do with matching child rows:

| Action | On DELETE | On UPDATE |
|---|---|---|
| **RESTRICT / NO ACTION** | Reject deletion if child rows exist | Reject update if child rows exist |
| **CASCADE** | Delete child rows automatically | Update FK value in child automatically |
| **SET NULL** | Set FK column in child to NULL | Set FK column in child to NULL |
| **SET DEFAULT** | Set FK column to its default value | Set FK column to its default value |

**Example with cascading actions:**
```sql
CREATE TABLE Department (
    dept_id   INT         PRIMARY KEY,
    dept_name VARCHAR(100)
);

CREATE TABLE Employee (
    emp_id    INT         PRIMARY KEY,
    emp_name  VARCHAR(100),
    dept_id   INT,

    FOREIGN KEY (dept_id) REFERENCES Department(dept_id)
        ON DELETE SET NULL       -- If dept deleted, set emp.dept_id to NULL
        ON UPDATE CASCADE        -- If dept_id changes, update emp.dept_id too
);
```

**Behavioral scenarios:**
```sql
-- DELETE parent row (dept_id = 1):
DELETE FROM Department WHERE dept_id = 1;
-- Result: All employees in dept 1 have their dept_id set to NULL

-- UPDATE parent PK (rename dept_id from 2 to 20):
UPDATE Department SET dept_id = 20 WHERE dept_id = 2;
-- Result: All employees who had dept_id=2 now automatically have dept_id=20
```

### Self-Referencing Foreign Key

A powerful use case — modeling hierarchical or recursive relationships within a single table:

```sql
CREATE TABLE Employee (
    emp_id      INT         PRIMARY KEY AUTO_INCREMENT,
    emp_name    VARCHAR(100) NOT NULL,
    manager_id  INT,         -- FK referencing the same table!

    FOREIGN KEY (manager_id) REFERENCES Employee(emp_id)
        ON DELETE SET NULL
);
```

**Data:**
```
Employee (Self-referencing)
┌────────┬──────────────┬────────────┐
│ emp_id │   emp_name   │ manager_id │
├────────┼──────────────┼────────────┤
│   1    │  CEO Alice   │   NULL     │  ← Top of hierarchy (no manager)
│   2    │  VP Bob      │    1       │  ← Reports to Alice
│   3    │  Mgr Carol   │    2       │  ← Reports to Bob
│   4    │  Dev Dave    │    3       │  ← Reports to Carol
└────────┴──────────────┴────────────┘
```

### Composite Foreign Key

When the referenced parent table has a composite primary key, the FK must include all columns:

```sql
-- Parent with composite PK:
CREATE TABLE CourseOffering (
    course_id   INT         NOT NULL,
    semester    VARCHAR(10) NOT NULL,
    room        VARCHAR(20),
    PRIMARY KEY (course_id, semester)
);

-- Child with composite FK:
CREATE TABLE StudentAttendance (
    student_id  INT         NOT NULL,
    course_id   INT         NOT NULL,
    semester    VARCHAR(10) NOT NULL,
    date_       DATE        NOT NULL,
    attended    BOOLEAN,

    PRIMARY KEY (student_id, course_id, semester, date_),

    -- FK must reference all columns of the composite PK:
    FOREIGN KEY (course_id, semester)
        REFERENCES CourseOffering(course_id, semester)
        ON DELETE CASCADE
);
```

### Significance of Foreign Keys
1. **Referential integrity**: Prevents orphaned records (child rows with no parent)
2. **Relationship modeling**: Represents one-to-many and many-to-many relationships
3. **Cascading maintenance**: Automates data consistency when parent data changes
4. **Documentation**: Explicitly declares relationships in the schema itself
5. **Query optimization**: DBMS optimizer uses FK relationships to plan efficient JOINs

# PART 4 — COMPARE & CONTRAST

## 4.1 Side-by-Side Comparison Table

| Feature | Candidate Key | Primary Key (Simple) | Composite Primary Key | Foreign Key |
|---|---|---|---|---|
| **Core Purpose** | Identify all minimal unique identifiers | Main row identifier | Multi-column row identifier | Link child to parent table |
| **Uniqueness** | Must be unique | Must be unique | Combination must be unique | NOT required (duplicates allowed in child) |
| **NULL allowed?** | No (conceptually) | No (strictly enforced) | No (all columns) | Yes, unless declared NOT NULL |
| **Number per table** | Many | **Exactly one** | Still one PK (multi-column) | Many (multiple FKs allowed) |
| **Columns involved** | One or more | Typically one | **Two or more** (by definition) | One or more (matching referenced key) |
| **Self-contained?** | Yes (within table) | Yes (within table) | Yes (within table) | No (references another table) |
| **Referencing role** | Can be referenced by FK | **Primary target** of FK | Target of composite FK | Does the referencing |
| **SQL constraint** | UNIQUE + NOT NULL | PRIMARY KEY | PRIMARY KEY (col1, col2,...) | FOREIGN KEY (...) REFERENCES |
| **Auto-indexed?** | Creates UNIQUE index | Creates PK index (clustered) | Creates composite PK index | Usually NOT auto-indexed |
| **Cascading behavior** | N/A | Cascade rules apply when PK is changed | Cascade rules apply | **Defines** cascade behavior |
| **Design stage** | Logical design | Logical + Physical design | Physical design (junction tables) | Physical design |
| **Scope of enforcement** | Within table | Within table | Within table | Across tables |
| **Typical use case** | Alternate unique identifiers (SSN, email) | Entity tables (Student, Employee) | Junction tables (Enrollment, OrderItem) | Relationship modeling |

## 4.2 Specific Utility & Significance Summary

### Candidate Key — Specific Utility
```
WHAT IT DOES:
  └─ Identifies ALL valid minimal identifiers in a table

WHY IT MATTERS:
  ├─ 1. Provides the pool from which PK is chosen
  ├─ 2. Guides normalization theory (BCNF is defined in terms of candidate keys)
  ├─ 3. Non-chosen candidates remain enforced as UNIQUE NOT NULL
  └─ 4. Multiple access paths to the same data (e.g., find student by SSN or email)

UNIQUE ADVANTAGE:
  The concept acknowledges that a table may have multiple valid identifiers
  and preserves all of them — not just the one chosen as PK.
```

### Primary Key — Specific Utility
```
WHAT IT DOES:
  └─ Provides ONE official, stable, non-null identifier for each row

WHY IT MATTERS:
  ├─ 1. Entity integrity — every entity instance is uniquely trackable
  ├─ 2. Is the primary JOIN anchor between tables
  ├─ 3. Is the target of all foreign key references
  ├─ 4. Auto-indexed for optimal performance
  └─ 5. Conceptually represents "this row's identity"

UNIQUE ADVANTAGE:
  It is THE designated identifier. Simple, single-column surrogate PKs
  (auto-increment integers) are the most efficient for widespread referencing
  across many child tables.
```

### Composite Primary Key — Specific Utility
```
WHAT IT DOES:
  └─ Enforces uniqueness across a combination of columns
     when no single column is sufficient

WHY IT MATTERS:
  ├─ 1. Naturally models many-to-many relationships without artificial columns
  ├─ 2. Prevents duplicate relationships at the database engine level
  ├─ 3. Self-documents the table's meaning (columns tell the story)
  └─ 4. Appropriate when the "identity" IS the combination

UNIQUE ADVANTAGE:
  The most semantically honest approach for junction tables.
  The key itself encodes the relationship — no surrogate needed.
  An Enrollment exists because a (student, course, semester) combination
  is its very definition.
```

### Foreign Key — Specific Utility
```
WHAT IT DOES:
  └─ Creates and enforces relationships BETWEEN tables

WHY IT MATTERS:
  ├─ 1. Referential integrity — no orphaned records
  ├─ 2. Enables meaningful JOIN operations
  ├─ 3. Cascade rules automate multi-table data consistency
  ├─ 4. Self-documents relationships in the schema
  └─ 5. Enables normalization (splitting data into related tables)

UNIQUE ADVANTAGE:
  It is the ONLY key type that operates across table boundaries.
  Without FKs, a relational database would just be a collection of
  isolated spreadsheets with no enforced connections.
```

## 4.3 The Contrast in One Scenario

**Question:** "Can we find a student, identify their enrollment, and ensure the enrollment references a real student?"

```
CANDIDATE KEY:
  student.ssn = '123-45-6789'
  → Can find the student by SSN (alternate identifier path)

PRIMARY KEY:
  student.student_id = 1
  → Official identifier; all other tables reference this value

COMPOSITE PK:
  enrollment(student_id=1, course_id=101, semester='Fall2024')
  → Uniquely identifies THIS specific enrollment record
  → Prevents Alice from being enrolled in CS101 in Fall2024 twice

FOREIGN KEY:
  enrollment.student_id = 1 → REFERENCES student.student_id
  → Guarantees that enrollment.student_id=1 corresponds to a REAL student
  → If student #1 is deleted, CASCADE removes her enrollments automatically
```

# PART 5 — QUICK REFERENCE & DECISION GUIDE

## 5.1 Key Selection Decision Tree

```
Does the attribute uniquely and minimally identify rows?
│
├── YES → Is it the "best" choice (stable, small, commonly referenced)?
│          ├── YES → Make it PRIMARY KEY
│          └── NO  → Enforce as UNIQUE NOT NULL (it's a Candidate Key)
│
├── NO (uniqueness requires multiple columns) →
│         Is there no good single-column identifier?
│          ├── YES → Create COMPOSITE PRIMARY KEY
│          └── NO  → Add surrogate PK + UNIQUE constraint on the combination
│
└── Does it reference another table's PK/Candidate Key? → FOREIGN KEY
```

## 5.2 Common Mistakes to Avoid

| Mistake | Problem | Correct Approach |
|---|---|---|
| Using mutable attributes as PK (email, phone) | If user changes email, all FK references break | Use surrogate (auto-increment) PK |
| Forgetting NOT NULL on candidate keys | UNIQUE allows NULLs; candidate key semantics violated | Use UNIQUE + NOT NULL |
| Not indexing FK columns | Joins, deletes become slow (full table scan) | Manually CREATE INDEX on FK columns |
| Over-using composite PKs | Complex FKs, verbose queries | Use composite PK only for true junction tables |
| No FK constraints (relying on app logic) | DB can become inconsistent | Always declare FK constraints for referential integrity |
| Making a large string a PK that's widely referenced | Bloated FK columns and indexes everywhere | Use surrogate INT PK; keep natural key as UNIQUE |

## 5.3 Final Summary in One Table

| Key Type | Defines... | Enforces... | Scope | SQL Keyword |
|---|---|---|---|---|
| **Candidate Key** | All valid minimal unique identifiers | Uniqueness + Not-Nullness within table | Intra-table | `UNIQUE NOT NULL` |
| **Primary Key** | The chosen main row identifier | Entity Integrity (unique + not null) | Intra-table | `PRIMARY KEY` |
| **Composite PK** | Multi-column row identity | Uniqueness of column combinations | Intra-table | `PRIMARY KEY (col1, col2,...)` |
| **Foreign Key** | Inter-table relationships | Referential Integrity across tables | **Inter-table** | `FOREIGN KEY...REFERENCES` |

---

> **Closing Thought:**
> Keys are the structural backbone of relational databases. **Candidate keys** establish what could identify a row. **Primary keys** (simple or composite) establish what does identify a row. **Foreign keys** establish how rows in different tables relate to each other. Together, they transform isolated tables into an integrated, consistent, and queryable relational model.
